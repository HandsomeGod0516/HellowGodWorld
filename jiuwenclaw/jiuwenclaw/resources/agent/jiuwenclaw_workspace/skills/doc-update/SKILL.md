# 文件更新

以**原始碼為唯一事實來源**，系統性核對並更新專案文件。保證多語言文件對齊、配置表準確、程式碼引用正確、章節編號連續。

## 核心原則

1. **原始碼即真理** — 預設值、列舉值、標誌列表一律以原始碼為準，文件記載不作為依據。
2. **多語言 1:1** — 每種語言的文件必須完整配對，發現缺口時須先向使用者確認，不自行補全。
3. **文件不寫版本號** — `vX.Y.Z` 很快過時，用功能描述替代。
4. **編號必須連續** — 插入/刪除章節後遞增所有後續章節號。
5. **就地修復** — 範圍和結構決策（更新哪些檔案、是否新建語言文件）需先確認；內容錯誤（數值、列表、編號）審計到即直接寫入，不等二次確認。

## 操作流程

> **讀取約束**：每次只讀 1–3 個檔案，避免單次讀取過多導致上下文溢位。

### 0. 確定範圍

若使用者未指定目標文件：

1. 搜尋專案根目錄下常見文件目錄（`doc/`、`docs/`、`README*.md`）
2. 列出找到的文件列表，請使用者確認本次更新範圍
3. 範圍確認後再進入後續流程，不自行決定

### 1. 清點與配對

列出所有語言的文件目錄，建立跨語言對映表，標出缺口。發現缺口時向使用者報告，不自行建立。

### 2. 提取原始碼事實

根據文件主題定位權威原始碼檔案。常見對照關係：

| 文件主題 | 權威原始碼 |
|---------|---------|
| 配置表 | 配置檔案、環境變數模板 |
| CLI / 命令 | 命令解析器、列舉定義、常量集合 |
| 模組功能 | 對應模組的入口檔案、列舉類、路由表 |
| API 文件 | 路由定義、介面描述檔案 |

在原始碼中搜尋關鍵符號，定位後讀取具體內容。

### 3. 逐檔案審計

**配置表審計**：
- 每個配置項在原始碼配置檔案中是否存在？
- 預設值是否與原始碼一致？（區分配置檔案預設值和環境變數預設值）
- 環境變數名是否與模板檔案吻合？
- 原始碼中已有但文件未收錄的新條目？

**程式碼引用審計**：
- 文件提到的類名、列舉成員、常量 → 與原始碼定義逐一核對
- 文件提到的檔案路徑 → 確認實際存在
- 文件描述的功能範圍 → 與原始碼實現比對，是否遺漏新增能力

**結構檢查**：
- 章節編號連續，無跳躍無重複
- 無過期版本標籤
- 交叉引用連結可跳轉
- 專有名詞/產品名稱全文統一

### 4. 修復

| 修復型別 | 操作 |
|---------|------|
| 補缺失章節 | 在正確位置插入，然後所有後續章節號 +1 |
| 修正數值 | 以原始碼值為準，覆蓋文件中的錯誤值 |
| 補全列表 | 新增遺漏的列舉成員、環境變數、配置項 |
| 移除版本標籤 | 去掉版本號，改用功能描述 |
| 修正錯別字 | 統一產品名、修正文字錯誤 |

**重編號要領**：插入新章節後，逐個修改後續章節號 +1，不得批次替換，以免誤改其他位置出現的相同數字。

### 5. 驗收

- 檢查所有標題編號，確認連續無重複
- 多語言文件數量與配對狀態符合步驟 1 的確認結果
- 抽查 2–3 處修復行確認內容正確
- 交叉引用連結可跳轉

## 常見陷阱

- **配置裡寫的 ≠ 執行時用的** — 配置檔案記錄相對路徑，執行時會拼接工作目錄字首（如 `agent/skills` → `workspace/agent/skills/`）。文件應記錄配置檔案中的原始值，而非執行時解析後的路徑。
- **配置註釋可能過時** — 註釋標註"60秒"但實際值為 `3600` 的情況較為常見。應以實際值為準，註釋不可作為依據。
- **區分配置變數和環境變數** — 僅出現在環境變數模板中、未在配置檔案中定義的變數，不應歸入配置表章節，應單獨放在"僅環境變數可配置"區域。
- **插入章節後需修改其後所有編號** — 不得僅修改下一節，其後各節的編號均需遞增 +1。
- **在 markdown 表格中做查詢替換須謹慎** — 表格每列用 `|` 分隔，搜尋短文字時易匹配到相鄰列的分隔符，應攜帶足夠的上下文以確保定位準確。
