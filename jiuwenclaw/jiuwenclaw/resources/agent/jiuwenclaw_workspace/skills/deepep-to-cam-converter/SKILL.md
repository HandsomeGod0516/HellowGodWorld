# CAM運算元替換專家技能

## 技能概述
本技能專注於將基於DeepEP的Mixture of Experts (MoE) 程式碼遷移至昇騰（Ascend）NPU環境。它能自動識別DeepEP dispatch & combine運算元，**嚴格基於程式碼的實際執行引數（而非預設值）**校驗CAM運算元約束。

**核心原則**：
- **思維鏈先行**：在執行任何程式碼修改前，**必須**先輸出分析過程和自檢結果。嚴禁直接生成程式碼。
- **原地修改**：預設直接在使用者指定的原檔案上修改，嚴禁建立新檔案（除非使用者顯式要求）。
- **動態值優先**：判斷約束時，必須追蹤引數的實際執行時值，**嚴禁**直接使用程式碼中的硬編碼預設值。
- **強制互動**：在運算元模式選擇（如A3普通 vs Shmem）和功能支援度處理上，**必須**詢問使用者，嚴禁AI自作主張。

## 工作流程

### 1. 程式碼掃描與依賴分析
#### 1.1 目標檢測
- **DeepEP識別**：掃描程式碼中是否存在`import deep_ep`及`dispatch`/`combine`相關呼叫。
- **MOE/EP模式識別**：確認程式碼是否涉及Mixture of Experts或Expert Parallelism邏輯。
- **無匹配處理**：若未檢測到相關程式碼，直接告知使用者並終止流程。

#### 1.2 依賴與上下文分析
- **匯入分析**：提取所有`import`語句，識別本地模組依賴。
- **通訊域掃描**：檢查是否存在`dist.init_process_group`、`backend='nccl'`、`torch.cuda.set_device`等特徵程式碼。
- **外部依賴檢查**：識別是否呼叫了外部初始化函式（如`utils.init_dist`），需同步分析這些函式的實現。

> **若“DeepEP 程式碼識別”為否，直接終止。若為是，繼續下一階段。**

### 2. 環境與策略決策
**注意**：此階段必須與使用者互動，不得跳過。

#### 2.1 環境選擇
向使用者展示以下選項，確定目標執行環境：
- **選項1**：基於當前環境自動檢測（嘗試執行`npu-smi info`，根據裝置型號判斷是A2環境或A3環境）。
- **選項2**：指定目標環境（使用者手動指定A2環境或A3環境，用於交叉編譯或程式碼預研場景）。

#### 2.2 引數值解析與約束校驗
**重要原則：程式碼中的預設值（Default Value）≠ 實際執行值（Runtime Value）**

在執行替換前，必須對約束條件涉及的引數進行**實際值溯源**：
1. **引數溯源**：
   - 檢查引數是否透過`argparse`、`config.yaml`或命令列傳入。
   - **嚴禁**使用 `parser.add_argument(..., default=XXX)` 中的 `XXX` 作為判斷依據。
   - **必須**假設程式碼中的預設值可能不是實際執行值。

2. **互動確認機制**：
   - 對於關鍵約束引數（如 hidden_size, top_k, expert_num 等），如果無法從程式碼邏輯中100%確定其執行時賦值，**必須**向使用者發起詢問：
     > “檢測到引數 [引數名] 在程式碼中的預設值為 [預設值]，但這可能不是實際執行值。請確認實際執行時的數值是多少？以便準確判斷是否滿足CAM運算元約束。”

3. **約束校驗邏輯**：
   - **情況A（值確定且滿足）**：使用者確認實際值，且滿足CAM運算元約束 -> **進入運算元模式選擇**。
   - **情況B（值確定但不滿足）**：使用者確認實際值，不滿足約束 -> **停止替換**，告知使用者不支援。
   - **情況C（值不確定）**：使用者未提供 -> **暫停替換**，標記該處需人工確認。

#### 2.3 運算元模式選擇
在確認引數值滿足約束後，根據目標環境確定具體運算元模式：
- **A2環境**：僅使用 **CAM A2 運算元**。
- **A3環境**：
   - 檢查程式碼是否同時滿足 **普通A3運算元**、 **Shmem運算元** 和**fused deep moe運算元**的約束條件。
   - 注意fused deep moe運算元替換有嚴格的約束正規化，請仔細閱讀說明文件，檢查是否滿足正規化，需要基於dispatch & combine函式去查詢呼叫鏈，檢視最終呼叫方是否滿足約束正規化
   - **阻斷規則**：**如果有多個都滿足，AI必須立即停止自動流程，並向使用者展示選擇題，等待使用者回覆，以三個條件都滿足的場景為例，可以展示如下選項**
     > **檢測到當前程式碼同時滿足多組運算元的約束條件，請做出選擇：()**
     > - **選項1（普通A3）**：引數配置簡單，無需額外共享記憶體初始化。
     > - **選項2（Shmem A3）**：效能更優，但需滿足特定約束及初始化。
     > - **選項2（fused deep moe運算元）**：效能最優，將通訊計算過程融合為一個大運算元。
     > **請回複選項繼續。**
   - **如果僅滿足其一**：自動選擇該模式並告知使用者。

#### 2.4 功能支援度分析與策略確認
在執行替換前，必須對比DeepEP原功能與CAM運算元支援範圍，並輸出分析報告。

1. **生成支援度報告**：
   - 分析程式碼中使用了哪些DeepEP特性, 當前cam對deep ep特性支援度如下
    | DeepEP特性 | CAM支援情況 | 詳細說明 |
    | :--- | :--- | :--- |
    | 低延遲模式 | 不支援 | CAM 不支援低延遲模式。若檢測到 low_latency_mode=True 或相關邏輯，必須標記為不相容。警告使用者將使用非低時延模式替換 |
    | 精細化調優 | 不支援 | CAM 遮蔽了底層效能引數配置。若程式碼中顯式傳入了 Config 物件或 num_sms, buffer_size 等調優引數，需自動忽略這些引數並警告使用者，改用 CAM 預設配置。|
    | 非同步控制流 | 不支援 | CAM 不支援 Event 物件作為返回值。若檢測到 event = dispatch(...) 或 event.wait()，移除所有 Event 相關的變數定義和等待邏輯。警告使用者：通訊與計算的重疊控制將被移除，運算元將按預設同步/非同步策略執行。|
   - 列出 **支援替換的部分** 和 **不支援替換的部分**。

2. **使用者確認策略**：
   - 如果存在 **不支援替換的部分**，**必須**向使用者展示以下選項，等待使用者回覆：
      檢測到CAM運算元對當前程式碼的支援情況如下：
      - **支援替換的部分**：[列出具體功能/程式碼行]
      - **不支援替換的部分**：[列出具體功能/程式碼行]
      請選擇處理策略：
      - **選項A**：停止替換，不做任何修改。
      - **選項B**：替換支援的部分，**保留**不支援的功能程式碼不變（混合模式）。
      - **選項C**：替換支援的部分，**刪除**不支援的功能程式碼。

### 3. 執行替換與轉換
#### 3.1 通訊域轉換（NCCL -> HCCL）
**執行範圍**：目標檔案及所有識別到的本地依賴檔案。

| 原始碼特徵 (CUDA/NCCL) | 替換後程式碼 (NPU/HCCL) | 備註 |
| :--- | :--- | :--- |
| `backend='nccl'` | `backend='hccl'` | 核心通訊後端 |
| `torch.cuda.set_device(x)` | `torch.npu.set_device(x)` | 裝置繫結 |
| `torch.set_default_device('cuda')` | `torch.set_default_device('npu')` | 預設裝置 |
| `torch.device('cuda:0')` | `torch.device('npu:0')` | 裝置物件 |
| `tensor.cuda()` | `tensor.npu()` | Tensor遷移 |

#### 3.2 運算元介面替換
根據使用者確認的CAM運算元模式（A2/A3/Shmem）和策略（保留/刪除），執行以下操作：
- **匯入替換**：將`import deep_ep`替換為cam對應庫,注意cam庫依賴torch_npu,必須先import torch_npu然後import umdk_cam_op_lib。
- **介面對映**：將deep ep dispatch & combine等相關運算元對映為對應的CAM介面呼叫。
- **引數調整**：根據CAM運算元文件調整引數順序和命名。
- **程式碼處理**：
   - 若使用者選擇 **保留**：保留原DeepEP程式碼塊，新增註釋 `# CAM Migration: DeepEP code retained due to unsupported feature`。
   - 若使用者選擇 **刪除**：刪除不支援的功能程式碼。
- **冗餘清理**：刪除原DeepEP特有但CAM不需要的引數構造程式碼。
  **資源釋放** 通訊域釋放和shmem的釋放(aclshmem_free和aclshmem_finialize)必須在運算元執行結束，即torch.npu.synchronize()等同步操作之後
> **🛑 階段 3 自檢**
> 在結束前，請簡要確認：
> - [ ] 所有 `nccl` 已替換為 `hccl`
> - [ ] 所有 `cuda` 已替換為 `npu`
> - 介面入參形狀和型別和介面文件要保持一致
> - 如果使用shmem，需要保證shmem資源釋放(aclshmem_free和aclshmem_finialize)要在運算元執行結束之後，即torch.npu.synchronize()等同步操作之後
> - 狀態：[透過/失敗 - 若失敗請停止,針對不滿足項重新執行階段3]
